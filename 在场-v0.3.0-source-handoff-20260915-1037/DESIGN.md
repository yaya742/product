## 主张

帮助在校学生在“眼前有很多事，但不知道先做什么”的时刻，用一句话得到一个有依据、可以改变的下一步。复杂性由系统承担：整理意图，查看相关资料，给出清楚建议。用户不需要先管理一个复杂工作台。

这是基于用户明确描述的产品方向和截图进行的设计判断，尚无访谈、留存或满意度实验。用户本轮给出的真实反馈是：初始输入区偏窄，全屏后的内容太小，阅读费力；语音、图片、文件需要协调而可发现的入口。该反馈直接促成响应式比例的重做。

## 0.1.0 当时的工作取舍（非 L1 原则清单）

1. **先有帮助，再逐渐了解。** 不先问性格问卷。默认不挤占休息、不贴人格标签，记忆只来自明确表达。检验：空白 profile 也能开始；每条记忆可撤销和改正。
2. **一个入口，信息按需出现。** 主界面只保留聊天与少量例子。连接、资料、记忆和安排在使用时展开。检验：不用理解 obligation、工具注册或子代理术语也能操作。
3. **建议必须让人有掌控感。** 处理过程可查看、停止、重试；保存动作由用户选择，草稿不会因重试或换对话丢失。真实性与控制高于装饰上的简洁。
4. **舒适比展示功能更重要。** 中性石墨背景、统一中文字体、克制的中灰强调层。大屏放大输入区和文字，但长回复保留适合阅读的行宽。动效短、可中断，并尊重减少动态效果。

## Apple 原则如何落到行为

依据 [Apple Design foundations](https://developer.apple.com/videos/play/wwdc2025/359/) 对结构、导航、内容与渐进披露的说明，连接页被简化为一条 DeepSeek 路径，模型和测试折叠，校园资料独立进入；完成后的建议由大卡片收成结果条。

依据 [Apple Motion](https://developer.apple.com/design/human-interface-guidelines/motion)，展开与关闭表达层级，持续操作不加表演性动画；停止无需等动画完成，减少动态效果同时影响弹窗和程序化滚动。依据 [Apple Materials](https://developer.apple.com/design/human-interface-guidelines/materials)，模糊仅用于临时面板的层次，正文与输入区维持稳定实底和可读对比。

用户明确要求 Apple 感而非 Windows 控件观感，因此采用中性灰的窗口控件，并始终显示关闭、最小化和最大化符号；保留名称和键盘能力，不用红绿灯颜色制造额外注意力。这是按用户偏好做的视觉取舍，不声称获得 Apple 认证或逐条符合所有平台的 HIG。没有提供独立 Sketch 文件；本轮对照的是指定的 product-design-director 技能、用户截图和 Apple 官方材料。

## 视觉复审增量（2026-09-10）

用户复审指出浅色外观中存在文字褪色、红色焦点、黑色强边框、绿色状态强调、同级操作错位和过程实线抢注意的问题。本轮将外观重做为两套独立中性语义层：深色使用石墨与浅灰，浅色使用暖白底与中灰正文；不把蓝、绿、红作为内容品牌或成功主色，只有窗口控件保留平台约定的红/黄/绿三色。输入焦点只在圆角容器外保留柔和中灰光晕，内部文字区域不再出现方形边框；过程详情使用低对比虚线分组，勾号用中性灰并同时保留文字状态。窗口控制始终显示符号，避免只靠三个无意义色点。

本轮新增证据：`artifacts/review/round14`（Electron 首页、对话、资料页、680×570、全屏与浅/深色首页）和 `artifacts/review/theme-check`（浅/深色对话、聚焦、高对比度）。这些证据证明当前渲染的局部状态与对比度方向，不能替代真实用户研究、VoiceOver 或所有平台的原生窗口审查。

本次 Harness 整合按两轮重新设计收敛：第一轮把校园读取、历史、天气、行动和分身归并为少量高层工具，并把连接器变成外部只读源；第二轮根据实际浅/深色截图和用户反馈，去除内容区的高饱和色、把窗口控件改为带符号的平台语义、把焦点与过程线改成低干扰中性样式，并把内部步骤计数收成一句用户语言，再重跑最小窗口、连接器、地图隔离回归和高对比检查。两轮都保留旧截图为历史证据，不把旧渲染当当前版本。

## Hermes harness 的取舍

参考 [Hermes architecture](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)、[Persistent memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory) 及仓库固定版本 `bf53ff00a7360826ec2c9e2949533160068a8fc8`。实际阅读了 `tools/registry.py`、`tools/delegate_tool.py`、`tools/delegate_tool_toolsets.py`、`tools/session_search_tool.py`、`agent/memory_manager.py` 与 `agent/context_compressor.py`。

| 成熟机制                     | 本项目的精简实现                                                              |
| ---------------------------- | ----------------------------------------------------------------------------- |
| 稳定提示词与 profile 快照    | 一轮内固定系统提示和小 profile；动态资料按需检索                              |
| 短记忆与完整历史分层         | 最多 1200 字、16 条偏好；SQLite 全文索引与中文短词检索保存原对话              |
| 注册表与 availability gating | Zod 参数验证；关闭的天气/记忆不进入工具 schema；缺数据返回 unavailable        |
| 独立分身只返回结果           | 同一 DeepSeek 模型，最多 3 路并行，只读工具，无递归派生、写记忆或外部操作能力 |
| 可观察、可中断循环           | 真实事件形成步骤摘要；AbortSignal 传播到请求、工具和分身                      |
| 上下文整理                   | 长会话中较早的内容生成摘要，原文继续可检索；接受的用户输入不被静默截断        |

这是针对本产品重写的精简实现，不是直接打包 Hermes，也不声称具备 Hermes 全部能力。每轮上限为 8 次主循环、20 次模型请求、2 次分派、每个分身 4 轮，整轮 240 秒。只读调用可并行；写入和用户动作保留明确边界。没有直接复制 Hermes 源码。

## 当前数据流

聊天框 → 校验输入并保存 → 固定基础提示词/偏好/当前会话 → DeepSeek → 工具请求 → 校园快照/历史/已授权天气或只读分身 → 综合回复与行动草稿 → 用户选择保存。

前端不持有 Node 能力，不接收存储中的 API Key。特权操作通过受校验的 IPC 进入主进程；使用自定义本地协议、CSP、contextIsolation 和 sandbox。参考 [Electron security](https://www.electronjs.org/docs/latest/tutorial/security) 与 [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)。

DeepSeek 参数依据 [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/) 与 [2026-09-10 官方多模态更新](https://deepseek.com/news/deepseek-v4-1-flash/)：标准 SSE 和工具结果回填；界面不展示或存储 reasoning_content。当前官网模型由宿主固定为 `deepseek-flash`，存量设置和高级设置不能替换。图片与用户文字作为同一条多模态消息发送，不使用预描述/向量中间层。

## 扩展边界

校园连接器下一步应产出带来源、时区和逐次 occurrence ID 的标准快照，调停课和假期由真实学校数据体现，不能从静态周课表猜测。校园地图需要通行拓扑和有效限制，不能从地点描述杜撰路径。预约、邮件、钉钉等写操作应先形成可审阅对象，再接明确授权和幂等提交。

手机 GPS、健康、日记需独立的设备端与逐类授权。主动提醒当前只覆盖应用运行期间的本地已定时安排；未来的天气/体育/考试判断需要可靠数据新鲜度、去重、安静时段和恢复机制。这些都未伪装为本 demo 已完成能力。

## 当前校园工具整合（2026-09-10）

用户明确要求当前私有单用户阶段优先读取本人全部校园资料，并把工具调用隐藏在单一聊天入口之后。模型只看到少量高层工具：`look_up` 统一处理校园、历史和天气资料，`prepare_action` 准备本地下一步，`delegate` 才启动有边界的只读分身；连接器内部仍保留 overview/detail/refresh 分层，但不把内部端点名暴露给模型。读取器由用户提供的 GPL 外部 `zju.py` 进程承担，Electron 不复制/链接其源码、不把密码传给模型。

这项整合改变了当前策略中的“接入边界”，没有改变 P1–P5：读取仍然是本人范围、来源和完整性可见、预约/签到/支付/修改资料没有工具；连接器缺失或认证失败不阻塞无关聊天。全量读取指本机连接器建立完整加密数据集和分域摘要，不指把全部原始字段塞进每次 DeepSeek 上下文或一次性显示给用户。

### 0.3.1 后端贯通后的前台修订（本轮）

本轮用户处境被具体化为：学生在一句自然话里同时表达情绪、一个低风险本地委托或一段对外草稿；他需要知道在场到底听到了什么、哪些资料被使用、动作是否真的写入，以及怎样撤回或处理未知结果。产品主张保持为“先让眼前的生活少解释一步，再把必要的控制留在手边”，而不是把内部 Harness 对象搬到前台。

前端阶段采用 M3（建议／接受／执行／回执分开）、M4（保住当前工作并可恢复）、M7（个性化可纠正且按任务最少使用）和 M8（运行、截取、打开图像、操作、修正、复查）；director 方法用于检查主张、关键兑现时刻和因果一致性。新增的局部表达是：

- 本机 direct_local 动作只有在 `confirmed_success` + `local_saved` 回执后才显示“本机已登记”，并同时给出回执时间、安排入口和“撤销登记”；失败、unknown、无法核查分别进入警示/原服务确认路径，不显示绿色成功语气。
- `ReplyEvidence` 展示不含原文和隐藏思维的“本轮理解”摘要（参与方式、片段数量、未决指代）以及对外草稿的收件人、目的、允许事实、语气和“仅草稿／发送服务未接入”状态。它让用户能纠正边界，但不把内部 ID、scope 或模型链展示出来。
- “可以接着聊”恢复入口优先使用最近焦点会话，保留后端 ConversationFrame 的跨会话锚点；范围和来源仍以原有渐进披露面板承载。

实际证据包括真实 Electron 合成数据的 [本轮理解截图](artifacts/harness/frontend-review/06a-interpretation.png)、[本机回执截图](artifacts/harness/frontend-review/06b-local-receipt.png)、[安排与未知回执截图](artifacts/harness/frontend-review/06c-agenda-receipt.png)、[公开草稿范围截图](artifacts/harness/frontend-review/06d-release-spec.png) 和 [公开草稿完整回归截图](artifacts/review/round1/06b-release-spec.png)、[停止恢复截图](artifacts/review/round22/06-stopped.png)，以及 `npm run test:harness:desktop` / `npm run test:desktop` 的报告。这些证明了当前实现的可见层级和具体操作，不证明真实学生满意度、真实 DeepSeek 语义质量或真实外部服务送达；`test:desktop` 的一次启动等待超时后连续重跑通过，保留为环境/时序观察而非产品成功证据。

本轮没有改变现有地图视觉系统、技术栈或受保护原则。已用真实 DeepSeek 做有界的人类体验样本，观察到回复长度、情绪承接、隐私草稿和工具轮重复的方向性改善；仍待独立人类复核：真实对外草稿在不同受众下的长期理解、学生是否会使用撤销/纠正入口，以及跨设备/真实通知服务的体验。

### 0.3.2 全量界面回归与记忆页减法（本轮追加）

用户明确指出：当“正在使用／待确认／已停用／原文依据／尚未核验”等工程分类并列出现时，用户要同时处理多个问题，视线没有一个自然落点。本次把这个反馈当作信息架构问题，而不是再加一层说明。

调整后的记忆页只在首屏回答一个问题：**哪些内容现在会帮我回答？** 当前理解直接列出；待确认、已停用和待整理内容合并为一个“其他内容”入口，展开后再按任务需要查看。原文、核验状态、时间条件和删除/改正操作仍保留在单条详情里，但不再作为首屏的平行导航。新增入口改成“告诉在场一件事”，避免把用户带进产品术语。

同一轮的对话来源条也做了减法：收起时只保留一个“本轮范围／群消息草稿／公开草稿”主标签，来源数量、参与方式、未决指代与披露边界放进展开层；用户先看到下一步和结果，需要审查时再进入细节。

实际复查了入口、浅/深色、对话、建议/回执、安排、连接、校园资料、偏好、记忆、记忆次级展开、历史空态、停止恢复、窄窗、最小窗和全屏；[新版记忆页首屏截图](artifacts/harness/frontend-review/02-understanding-light.png) 与 [次级内容展开截图](artifacts/harness/frontend-review/02-understanding-expanded.png) 显示首屏只保留一条主列表与一个次级入口，`npm run test:harness:desktop` 与 `npm run test:desktop` 继续通过。这个结论是启发式视觉与操作证据，不是学生审美研究；后续若真实用户仍无法找到待确认内容，再调整“其他内容”的命名或入口，而不是恢复四栏并列。

#### 交接给未来 Agent：不要回退的经验

- 不要把后台对象的生命周期直接做成前台导航。用户不需要先理解“候选／核验／派生／来源链”，只需要知道“现在会怎样影响我、我要不要改”。
- 不要在一个横向条里同时放范围、参与方式、来源数、受众、状态和操作；默认收起为一个主标签，详情再展开。
- 不要把所有记忆都当成同一种“档案”展示。当前有效、等待决定、停用和待整理的处理逻辑可以存在于后台，但前台首屏只展示与当下有用的内容。
- 不要因为担心隐藏信息而把所有信息同时放出来。渐进披露必须保留来源、权限、错误、撤销和未知的可发现入口；“更多”里应有明确的下一步，而不是一堆说明。
- 不要用庆祝、颜色、旋转或“已完成”文案替代真实回执。直接本地登记要给回执和撤销；外部未知要停止重发并说明去哪里核查。
- 不要把 Apple 感实现成白底、圆角、灰色和动效的拼贴。借鉴的是因果、连续、直接操作和安静层级；每个视觉细节都要服务用户此刻的注意力。
- 不要把一次截图或一次脚本通过写成用户偏好。没有访谈/实验就写“启发式证据”；下一轮先观察用户是否少解释、少重复、少看无关信息。

证据等级：**E0 原规则可追溯但未采用；E1 可确认已采用；E2 观察到局部效果；E3 经实际反馈或比较验证；E4 新提出待验证。** “读过原文”“当前选择与之相符”“原文实际支配了历史选择”“选择改善体验”不是同一强度。无法独立恢复历史因果时，只写当前一致性或前轮记录所声称的采用。

## 0.3.0 Harness · 从范围到可纠正的理解

本次是已授权的体验设计并实现。用户是正在处理校园事项、又不断补充“今天不同”“之前说错了”的学生；原型已有输入、历史、地图和安排，新的进展是让这些变化能被看见、改正，并停止影响旧建议。替代办法是每次重新解释、手工查历史或放弃个性化；是否降低真实学生的解释负担仍待用户研究。

本次主张：在继续得到帮助时，让学生看清正在使用什么理解，并能用一句话或直接操作改正它。范围和状态需可见，正文阅读和草稿连续性仍优先。方向已由用户任务和现有产品明确，本次没有另做三套视觉主题或重开产品发现。

严格阶段顺序：先完成后端，`artifacts/harness/backend-gate-restart-fixed/` 中 148 项测试及原有 17 项核心测试、真实连接/重启回归通过后，才读取项目 product-design 与用户指定的 product-design-director。前端阶段后续发现的问题继续回到相应后端接口修复并回归；没有使用开发子代理。

### 真实检查与复查

具备并实际使用了四种能力：启动原 Electron、Playwright 截图、通过 view_image 打开截图、执行点击/输入/键盘/重启。第一轮看过首页、浅深色理解列表和纠正原话；第二轮看过修订后的理解列表、未知回执、条件安排/反馈、小窗口范围面板及深色临时对话。

观察后修复：待确认的搬家记录曾显示“通常适用”，改为“适用范围待确认”；停用记录曾抢在正在使用记录前，改为状态排序；新范围面板浅色下拉框曾为深底黑字，改用语义颜色；临时示例不再给出与“不保存”承诺矛盾的保存安排按钮；校园账号连接取消或未完成时曾误报“已登录”，现改为依据后端返回状态显示“登录未完成”；第三方插件入口曾只写“安装插件”，现改为“导入插件包”，并在宿主校验后展示可审查的插件摘要，普通 ZIP 不再有机会进入安装流程。全屏 1536 CSS 像素时输入字号此前不足已有 17px 回归门槛，调整后实测约 17.22px，保持 900px 阅读上限。

### 0.3.0 悬停控件的轻量化增量（2026-09-15）

用户指出浅色外观中多个按钮悬停后接近纯黑，尤其顶部“新的对话”图标出现深色方块，图标本身又不够突出。本次将图标、建议和次要按钮的悬停背景统一为炭灰 `#454745`，前景切换为浅色；关闭按钮继续保留红色语义，主要提交按钮不改变原有浅色反馈。颜色放入 `tokens.css` 的控件变量，避免各按钮继续分散使用近黑字面量。

已在真实 Electron 的浅色主题中触发“新的对话”悬停，检查到背景 `rgb(69, 71, 69)`、前景 `rgb(247, 248, 247)`，并通过 `scripts/check-theme.mjs` 固化断言。该证据覆盖当前首页和指定主题，不等于所有平台、所有高对比度设置或学生审美满意度测试。

当前证据是合成任务、代码/协议检查、本机视觉观察和一组真实 DeepSeek 有界对话；没有真实学生访谈、满意度实验、独立无障碍审计或可复现的模型语义/体验结论。E1/E2 不能提升为这些方面的 E3；主代理逐条复核见 `artifacts/harness/conversation-quality-final/HUMAN-REVIEW.md`。未来若学生无法找到更正入口、误把条件安排当确定计划，或仍反复解释同一事实，应针对这些行为重新验证和修订设计。

### 0.3.0 官网多模态图文输入增量（2026-09-12）

本轮使用 M2、M4 和 M8。用户已有“＋”附件入口，因此没有新增相机按钮；只在原菜单中把“添加图片”与文字文件并列。发送前保留原长条草稿预览。发送后初版曾把图片和文字放进同一大气泡，用户指出过大且与背景/文字框粘连；复查发现 `harness.css` 的旧直系选择器误命中新外层。最终改为靠右的紧凑图片缩略图和独立文字气泡；用户只在发送后手动点击缩略图时才打开大图预览，可用 Esc、关闭按钮或点背景退出。PDF、压缩包和通用文档未因此冒充为已支持；后续应使用紧凑文件卡，不套用图片预览。

模型能力先通过 `scripts/probe-deepseek-vision.mjs` 直连官网验证：图像中的“圆点在右半边”被用来选择“右侧通行”，并转换为日常提醒“门把手在右边，晚归记得带钥匙”，证明这次有界输入能联合遵循文字规则，不只是自动图片描述。第二道验证由 `tests/multimodal-ui.mjs --live` 经真实 Electron 的文件选择、IPC、Harness 和 DeepSeek 完成；请求中实际是 `deepseek-flash`、1 个 text part 和 1 个 JPEG image part，官网返回了基于右侧视觉位置的钥匙提醒。浅色、深色、700px 窄窗、发出后缩略图和点开大图均由真实 Electron 截图后打开查看，证据在 `artifacts/review/multimodal/`。这是单张合成图的有界成功，不代表任意 OCR、医疗图像或所有视觉推理都正确。
