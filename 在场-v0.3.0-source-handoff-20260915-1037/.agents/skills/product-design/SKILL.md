# 本项目的设计方法

使用当次任务、真实产物和允许读取的证据；不复制外部设计 Skill 全文，不把本项目当前颜色、组件、模型或像素数变成原则。完整路径与集成状态查[项目导航](../../../PROJECT-NAVIGATION.md)。

## 先决定本次设计深度

说明学生在什么处境下需要得到什么结果，以及本次属于探索、体验设计、已授权实现还是局部评审。已明确的小修只读有关方法；重大取舍再查 [project-foundations](../project-foundations/SKILL.md)。当前策略要求以自然语言为主要入口；重新设计可替换整个实现，不自动等于放弃当前明确策略。

## 按问题选方法

| 方法 | 何时使用、改变什么 | 如何检查；不适用时的替代 |
| --- | --- | --- |
| M1 先得到一次有效帮助 | 注册、连接、个性化输入挡住开始时，减少首轮必答内容，只问会改变当下结果的信息 | 用无 Profile 和部分拒绝授权的任务走一遍；若某任务确实需要认证或关键信息，说明必要性后补问，不用假结果替代 |
| M2 按任务披露信息 | 连接、设置、来源或内部步骤争抢注意力时，先明确主要内容和下一动作，再选择分组和展开方式 | 核对状态、来源和退出是否可发现；高频比较、大量结构化编辑可用列表或直接操作，不把所有结果硬塞进对话气泡 |
| M3 分清建议、接受与执行 | 推荐、保存、本地完成、外部预约可能被混读时，让文案、对象和回执对上真实状态 | 逐一检查尚未连接、未授权、已准备、已接受、执行中、结果未知和完成；没有实现的状态先写契约，不伪造“已完成” |
| M4 先保住用户正在做的事 | 切换、重试、取消、失败或输入法操作可能造成丢失时，把草稿和附件归到正确会话，反馈贴近触发点 | 用合成资料检查重试不带错附件、返回焦点、取消与超时；若当前平台机制不同，选择同样可恢复的做法，不照搬某个组件 |
| M5 分开输入空间与阅读舒适度 | 窗口放大后内容过小，或长回复过宽时，分别检查输入区域、正文行长、字号与节奏 | 查看目标窗口、全屏和真实长内容；固定数值只属于当前实现，不能直接复制到手机、其他屏幕或不同密度任务 |
| M6 动效解释变化，不增加负担 | 展开、收起、等待和状态转换容易迷失时，用简短且可打断的反馈表达因果 | 实际操作并检查减少动态效果、键盘、停止和焦点；快照只能证明静态表现。无明确收益时可不加动画，不能把固定缓动曲线当 Apple 原则 |
| M7 个性化可变且最少够用 | 偏好、当前情绪、官方记录或人格倾向被混为一谈时，先按导航 User 边界归属，再决定展示与更新 | 用“今天不想跑／长期不喜欢／不要再提醒／官方计入一次”对比；这轮有些更新链仅为要求或建议，不能用 Skill 文字声称已实现 |
| M8 证据决定改进与停止 | 初版“看着不错”但缺运行、对比或真实反馈时，把观察、解释和待验证假设分开 | 在授权与工具允许范围内：运行 → 捕获 → 真正看图 → 操作关键任务 → 修正 → 复查；本轮只准文档时读既有证据，不启动真实数据流程。未检查处明确保留，低收益风格偏好不触发无限重做 |

## 证据与修订

每条重要建议只保留足够追溯的信息：来源条款、所解决的问题、取舍、产物、保护的原则、证据等级及适用条件。等级使用“原规则可追溯但未采用／可确认已采用／观察到局部效果／经实际反馈或比较验证／新提出待验证”。代码采用不能推出改善；真实问题反馈也不等于改后满意度。

先前的 redesign、Apple 风格、灰色窗口控件和具体尺寸是实现选择，不是每次局部改动都要重复的固定仪式。若需修改方法，说明新的情境、反例和证据；不能借方法修订悄悄改产品范围。

## 完成标准

说明这次用了哪些相关方法、改变了哪个用户处境、实际看过／操作过／运行过什么、还缺什么证据。准确区分“设计要求”“当前实现”“本次验证”。对照导航中的已知差距，不宣称 UI、Skill 或系统提示词单独实现了数据最小化、遗忘或授权保证。

## 在场专属前台宪章（长期适用）

这部分把本项目已经得到的真实回归经验固化下来。它不是新的运行时权限，也不能覆盖 `project-foundations` 的 P1–P5；它约束前台的信息层级、文案和交互取舍。

### 1. 先做减法，再决定怎样解释

在场的用户通常只想把眼前的生活往前推进一步，不想阅读产品如何实现。每个页面和每个状态先写一句“用户此刻要知道什么”，然后只保留：

1. 一个视觉焦点；
2. 一个主要动作；
3. 一个明确退路或恢复动作。

如果同一行出现三个以上同权重标签、状态、按钮或解释，先假设信息架构有问题。把次要内容合并为一个自然的“查看详情／其他内容／更多资料”入口；不要用更小的字号、更多颜色或更多卡片解决拥挤。

### 2. 用户语言优先，工程状态后台化

默认界面不出现或不突出：`scope`、`epoch`、`receipt`、`candidate`、`provider`、`coverage`、`obligation`、`source ID`、`正在使用／待确认／原文依据／尚未核验` 这类面向工程师的生命周期标签。它们只有在用户主动核查来源、纠正理解、处理未知结果或修改数据时才以自然语言出现。

优先写：

- “现在会帮你回答的内容”而不是“正在使用的断言”；
- “还有一件事等你确认”而不是“candidate”；
- “本机已登记，可撤销”而不是“Action succeeded”；
- “结果还不能确认，请到原服务查看”而不是“unknown receipt”。

状态不能被隐藏：简洁来自渐进披露，不来自删除权限、来源、错误或撤销。

### 3. 记忆页的唯一首屏问题

记忆页首屏只回答：**哪些内容现在会帮到我？**

- 当前有效内容直接列出，按对当前生活的帮助排序，不按数据库状态堆四个并列栏目。
- 待确认、已停用、待整理统一放到一个次级入口（当前实现为“其他内容”）；展开后再分组。
- 单条内容默认只显示原话意义；条件、时间、来源、核验和删除/改正操作放在展开详情。
- 不把一次情绪、一次例外或第三人信息做成醒目的长期标签。
- 添加入口使用用户语言（当前为“告诉在场一件事”），不要求用户理解“记忆对象”或“断言”。

### 4. Apple 式体验的可迁移部分

可以借鉴 Apple 等平台的通用经验：直接操作、因果一致、连续反馈、安静但可发现的层级、可打断的动效、稳定的阅读节奏和熟悉控件。不要复制品牌皮肤，也不要把圆角、字体、颜色、模糊或某条缓动曲线写成原则。

“动态”只在它解释变化时存在：打开详情、切换范围、保存、撤销、返回和恢复要让人知道发生了什么；加载未知就显示诚实的等待或缺口，不制造装饰性循环。所有动态状态检查减少动态效果、键盘焦点、窄窗和长内容。

### 5. 每次设计回归的最小清单

- 入口：第一次打开是否能直接开始，不先读设置说明？
- 对话：收起状态是否只有一个重点？展开后是否仍能找到来源、边界和下一步？
- 记忆：首屏是否只有当前有用内容和一个次级入口？
- 行动：建议、登记、执行、未知、撤销是否各自说清？
- 连接/资料/偏好：是否把设置分成用户能理解的任务，而不是内部模块？
- 历史/安排/地图：是否知道自己在哪里、接下来做什么、怎样返回？
- 失败/停止/恢复：是否保住草稿，且给出真实退路？
- 视觉：浅色、深色、窄窗、全屏、长内容、减少动态效果是否真正运行并打开截图查看？
- 低技术熟练度：不看开发文档，是否仍能完成核心动作？

没有真实用户研究时，写“启发式/合成 Electron 证据”，不写“用户喜欢”或“符合所有人审美”。
