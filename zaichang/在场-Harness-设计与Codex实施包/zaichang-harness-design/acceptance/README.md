# 验收资料怎么使用

`student-200-questions.json` 是从当前讨论逐字提取的假想问题；不是当前真实用户资料，也不是已经写好并运行的测试。

`scenarios.json` 是多轮状态验收规格。它定义合成初始状态、操作步骤、故障与可检查的预期；运行器需要在真实仓库实现。无需为此在生产产品里造一个复杂测试DSL引擎：使用类型化测试helper，将每个步骤映射到真实服务或UI动作即可。

## 不可偷换的绑定

`probe` 是测试诊断对象上的JSON Pointer。诊断值必须来自真实SQLite查询、实际ContextPack、provider请求拦截器、能力访问记录、HTTP sink和真实UI。不能根据case ID填写正确诊断；不能把expected送给被测LLM。`has_record`使用指定字段的子集匹配，`equals`使用深相等；长度操作允许数组或已计算计数。

有些probe为审计投影，例如把typed_value转成value，或把UI文案映射为规范状态。这种转换必须保持来自真实状态的单向映射，不能掩盖未知、错误或缺字段。未实现的probe按未完成处理，而不是跳过算成功。

## 初始数据和测试权限

全部fixture均为虚构，包括学校规则与体育次数。`history`由测试helper通过相同证据机制准备；`seed_assertion`须建立独立的合成来源和完整元数据，不伪装成生产用户原文。测试可直接seed已存在的历史状态，以测试某一后续机制，但不能seed本轮预期终态。

`seed_approved_action`只在受控测试服务内构建具体、有效、限于本地sink的授权，并绑定参数digest和policy epoch。它不能绕过生产审批，也不能开启真实网络写入。测试“执行前撤权”时，撤回之前必须确实具有对应授权，否则只是测试从未授权。

`set_tool_result`配置独立的受控Provider，不直接把结果写入最终ContextPack；结果仍通过真实Broker、schema与领域更新。`inject_candidate`用于验证候选之后的补检索，不作为真实LLM生成正确候选的证据。

## 隐私扫描边界

“仅本轮不保存”的canary扫描覆盖应用数据目录、SQLite/WAL、FTS、blob、队列、缓存、应用日志与配置的崩溃输出；不扫描本测试规格源文件本身。测试驱动在内存捕获合成payload可用于断言，不应让产品把真实会话内容默认落盘。持久测试报告只允许合成数据；真实模型评估另设脱敏策略。

## 两次不同的运行

`scripted_contract`只证明机制；`both`表示同一行为既需受控脚本测试，也应进入真实模型语义评估；`desktop`必须走实际Electron入口。它们均不表示本包已经完成对应运行。

结构门禁、语义评估、真实外部能力和用户体验证据分别报告。40方向全有对应关系，不意味着40方向的全部外部服务已经存在。
